# Media Format Conversion Design

## 背景

当前导出流程已经支持：

- 图片消息导出到 `images/`
- 语音消息导出到 `audio/`
- JSON 中写入相对路径 `file_path`

但现状仍有两个问题：

1. 图片目前大多直接复制源文件或缩略图，扩展名和实际内容格式不统一。
2. 语音目前导出的是原始 `.silk` 数据，不符合“导出为可直接使用的音频文件”的目标。

本次改动需要把媒体导出从“复制原始资源”升级为“按统一规则转码后导出”。

## 目标

- 语音消息导出为 `wav`
- 普通聊天照片导出为 `jpg`
- 带透明背景的静态图、表情、贴纸类图片导出为 `png`
- 会动的表情或动图导出为 `gif`
- 单会话导出和全量导出都统一使用同一套转换规则
- JSON 中继续写相对路径 `file_path`
- 单条媒体转换失败时不影响整批导出

## 非目标

- 不在本次中支持视频文件转码
- 不做截图语义识别，例如“长截图”和“普通截图”不单独建规则
- 不做图片画质增强、尺寸调整、去水印或压缩优化
- 不保证保留微信原始文件名

## 设计原则

### 1. 以内容特征而不是文件后缀决定导出格式

微信本地图片资源大量使用 `.dat` 或不稳定的命名方式，文件后缀不能作为可靠依据。

最终导出格式应基于解码后的图像内容判定：

- 有多帧动画：导出 `gif`
- 单帧且包含透明通道：导出 `png`
- 单帧且无透明通道：导出 `jpg`

这样可以自然覆盖：

- 普通聊天照片 -> `jpg`
- 静态表情/透明背景图/贴纸类图片 -> `png`
- 动图/会动表情 -> `gif`

### 2. 语音以可用格式为目标

语音消息的真实数据来自 `decrypted/message/media_0.db` 的 `VoiceInfo.voice_data`，这部分数据当前可导出为原始 `.silk`。

本次改动中，语音导出目标改为 `wav`：

- 从 `VoiceInfo.voice_data` 读取原始 Silk 数据
- 解码为 PCM
- 包装为标准 `wav`

JSON 的 `file_path` 将指向 `audio/.../*.wav`。

### 3. 单条失败不影响整批导出

媒体资源在真实数据中可能出现以下情况：

- 图片源文件存在，但无法正确解码
- 语音数据库有记录，但音频解码失败
- 文件能找到，但输出格式转换失败

遇到这些情况时：

- 不中断整次导出
- 当前消息 `file_path` 置为空字符串
- 文本占位内容保留，例如 `[图片]`、`[语音] 10"`

## 方案对比

### 方案 A：依赖系统工具最小拼接

思路：

- 图片用系统工具 `sips`
- 音频尝试用系统工具链转码

优点：

- 少引入 Python 依赖

缺点：

- 动图识别和透明通道判断能力不足
- 不能稳定处理 `.dat`
- 当前环境没有现成 Silk -> WAV 系统解码链

结论：

不选。图片和语音都无法稳定满足规则。

### 方案 B：引入可控的图像/语音解码能力

思路：

- 图片使用 Python 图像库做解码、动画检测、透明检测和重编码
- 语音使用 Silk 解码器将 `voice_data` 转成 PCM/WAV

优点：

- 行为稳定、可测试
- 能按内容特征而不是后缀决定最终格式
- 能同时覆盖单会话和全量导出

缺点：

- 要引入新依赖
- 需要处理解码失败回退

结论：

推荐并采用。

### 方案 C：只改图片，不改语音

优点：

- 实现简单

缺点：

- 不满足“音频需要转为 wav”

结论：

不选。

## 最终方案

### 媒体处理架构

在现有 `chat_export.py` 的媒体导出层之上增加一个“规范化导出”阶段：

1. 先按现有逻辑定位媒体源
2. 根据媒体类型分流：
   - 图片消息进入图像规范化流程
   - 语音消息进入音频规范化流程
3. 规范化完成后写入 `images/` 或 `audio/`
4. JSON 中写入新的目标文件路径

### 图片规范化流程

输入：

- `msg/attach/.../Img/...`
- `cache/.../Message/.../Thumb/...`
- 现有逻辑能找到的任意图片候选文件

处理步骤：

1. 读取原始文件字节
2. 尝试解码图像内容
3. 判断是否为多帧动画
4. 若非动画，判断是否存在透明通道
5. 按规则输出：
   - 动画 -> `.gif`
   - 静态透明 -> `.png`
   - 静态非透明 -> `.jpg`

输出命名规则保持现有风格，仍以消息标识为主，例如：

- `images/<session_hash>/<local_id>_<timestamp>.jpg`
- `images/<session_hash>/<local_id>_<timestamp>.png`
- `images/<session_hash>/<local_id>_<timestamp>.gif`

### 图片判定规则

使用以下固定规则：

- 多帧动画：导出 `gif`
- 单帧且透明：导出 `png`
- 单帧且不透明：导出 `jpg`

这意味着：

- 普通照片 -> `jpg`
- 大多数截图 -> `jpg`
- 静态透明表情 -> `png`
- 动图表情 -> `gif`

注意：

最终格式始终由内容特征决定，而不是由“截图”“表情”等语义标签决定；因此不透明静态图会导出为 `jpg`，透明静态图会导出为 `png`。

### 语音规范化流程

输入：

- `decrypted/message/media_0.db`
- `VoiceInfo.voice_data`

处理步骤：

1. 使用现有 `(username, local_id, create_time, svr_id)` 映射定位语音 blob
2. 将原始 Silk 数据解码为 PCM
3. 以标准 WAV 容器写出
4. 文件名统一为：
   - `audio/<session_hash>/<local_id>_<timestamp>.wav`

### JSON 结构

本次不新增复杂字段，继续沿用：

- `file_path`

示例：

```json
{
  "content": "[语音] 10\"",
  "file_path": "audio/82ff100bc35b06a13361b83d0ea8694c/896_1776912411.wav"
}
```

或：

```json
{
  "content": "[图片]",
  "file_path": "images/82ff100bc35b06a13361b83d0ea8694c/41_1776761550.png"
}
```

## 依赖策略

### 图片

需要引入图像处理依赖以稳定支持：

- `.dat` 解码后的实际图片识别
- 透明通道检测
- 动画帧检测
- `jpg` / `png` / `gif` 重编码

推荐依赖：

- `Pillow`

### 语音

需要引入 Silk 解码能力，把 `#!SILK_V3` 数据转为 PCM/WAV。

实现上要求：

- 在本地环境内可直接运行
- 不依赖系统预装 `ffmpeg`
- 可在测试中验证输出存在且为 `wav`

实现策略固定为：优先采用仓库内可控的 Silk 解码实现或显式声明的项目依赖，不依赖用户机器额外手工安装系统级音频工具。

安装文档需明确使用：

- `pip3 install -r requirements.txt`

依赖清单应显式包含：

- `pycryptodome`
- `Pillow`
- `silk-python`

## 错误处理

### 图片失败

如果图片文件：

- 找不到
- 无法解码
- 转码失败

则：

- `file_path = ""`
- 保留原始文本占位

### 音频失败

如果语音：

- `VoiceInfo` 没有匹配记录
- Silk 数据损坏
- 解码失败
- WAV 写出失败

则：

- `file_path = ""`
- 保留原始文本占位

## 对现有功能的影响

### 单会话导出

影响：

- `chat.json` 中图片和语音的 `file_path` 后缀会变化
- `images/` / `audio/` 中落地的不再是原始资源，而是规范化后的可用格式

不影响：

- `chat.txt`
- `chat.csv`
- 普通文本消息导出

### 全量导出

影响：

- 各会话 JSON 的 `file_path` 会从原始后缀变成目标格式后缀

不影响：

- 会话 JSON 文件命名
- `chatlab` / `meta` / `members` / `messages` 结构

## 测试策略

至少覆盖以下场景：

### 图片

1. 静态不透明图片 -> 导出 `jpg`
2. 静态透明图片 -> 导出 `png`
3. 多帧动画 -> 导出 `gif`
4. 找到图片源但解码失败 -> `file_path` 为空

### 语音

1. `VoiceInfo.voice_data` 存在 -> 导出 `wav`
2. 语音映射存在但解码失败 -> `file_path` 为空

### 导出链路

1. 单会话导出使用新格式规则
2. 全量导出使用新格式规则
3. JSON 仍写相对路径

## 风险

### 1. 依赖安装复杂度增加

图片和语音都需要新增解码能力，环境准备会比现在更复杂。

缓解：

- 优先选纯 Python 或仓库可控依赖
- 在 README 中直接指向 `pip3 install -r requirements.txt`
- 测试中覆盖最小可用路径

### 2. `.dat` 资源格式不稳定

不同微信版本可能有不同封装方式。

缓解：

- 以内容解码为准，不依赖文件后缀
- 保留失败回退

### 3. 语音解码器兼容性

Silk 数据存在版本兼容风险。

缓解：

- 先以当前真实样本验证
- 单条失败不影响整体导出

## 实施边界

本次实现只做以下交付：

- 图片导出统一转为 `jpg` / `png` / `gif`
- 语音导出统一转为 `wav`
- 更新 JSON `file_path`
- 更新测试
- 更新 README

不额外扩展：

- 视频转码
- OCR
- EXIF 保留
- 音频时长/采样率元数据扩展
